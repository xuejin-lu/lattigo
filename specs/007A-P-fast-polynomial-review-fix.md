## Blocking finding 1 — public output still full-copies dormant limbs

Current `circuits/ckks/polynomial/fast.go` ends `Evaluate` with:

```go
return result.CopyNew(), nil
```

and the degree-zero path similarly returns:

```go
return out.CopyNew(), nil
```

`CopyNew()` copies the structural ciphertext, including q2...qL rows. In Fast these high limbs are dormant/stale and must not be read/copied merely because they exist.

This violates the 007A storage contract:

```text
row exists structurally
!= row is authoritative
!= row must be copied
```

### Required fix

Return a public result whose storage ownership is independent of evaluator workspace, but copy only:

```text
q0/q1
metadata
Level/Scale/domain flags
```

A structural `ckks.NewCiphertext(..., result.Level())` allocation is acceptable because the current representation ties Level to row storage. The fix must avoid reading/copying q2...qL from the workspace result.

Prefer a narrow helper such as conceptually:

```go
func cloneMaintainedResult(params ckks.Parameters, src *rlwe.Ciphertext) *rlwe.Ciphertext
```

that allocates the structurally required public ciphertext and copies only maintained residues plus metadata.

Do not return evaluator-owned workspace directly if a subsequent `Evaluate` call could mutate a previously returned result.

Add a test that poisons workspace/output high limbs differently and verifies the public-copy operation does not deliberately synchronize q2...qL.

## Blocking finding 2 — missing end-to-end polynomial correctness oracle

The current `TestFastPolynomialRepresentativeDegree30` only checks structural properties such as:

```text
Degree
NTT/Montgomery
Level
```

It does not verify that the degree-30 Paterson-Stockmeyer result numerically equals the intended polynomial. Therefore the current tests do not prove the complete polynomial execution path is correct.

The existing `TestFastPolynomialPowerBasisQ01Oracle` validates only a small PowerBasis case and is not sufficient to validate baby-step + giant-step + coefficient accumulation end to end.

### Required tests

Add the following focused correctness tests.

### A. Non-power-of-two Chebyshev PowerBasis exact oracle

Exercise at least one non-power-of-two Chebyshev power such as `T3`, `T5`, or another power generated by the actual planner.

Build the reference directly from already-tested Fast primitives using the Chebyshev recurrence and compare exact:

```text
q0/q1
Level
Scale
Degree
```

This closes the original 007A requirement that recursive split / non-power-of-two generation be explicitly verified.

### B. Full Paterson-Stockmeyer numerical oracle

Create a legitimate Stage-A zero-secret-style polynomial input, not arbitrary random NTT residues, so the output can be interpreted numerically.

Preferred approach:

1. Encode deterministic small CKKS slot values using the ordinary CKKS encoder.
2. Construct a degree-one ciphertext-like input with the encoded plaintext in `c0` and zero in `c1` (consistent with the current zero-secret Stage-A semantics).
3. Ensure the Fast input is NTT + Montgomery and has sufficient Level for the polynomial depth.
4. Evaluate through `FastEvaluator.Evaluate`.
5. Decode only the authoritative q0/q1 result through a test/reference boundary. A temporary Level-1 plaintext/ciphertext carrying q0/q1 + output metadata is acceptable if it gives the correct CKKS interpretation. Test/reference-only reconstruction/materialization is also acceptable.
6. Compare decoded values against clear evaluation of the same `bignum.Polynomial` at the same transformed input values, using a CKKS-appropriate numerical tolerance.

The test must exercise both baby-step and giant-step logic.

### C. Representative degree-30 Chebyshev numerical oracle

Use a degree-30 Chebyshev polynomial representative of the Bootstrap Mod1 polynomial stage and validate numerical output, not only metadata.

Prefer one of:

```text
- the actual/default CosDiscrete degree-30 coefficient set generated by current bootstrapping/Mod1 parameter code, if this can be done without an import cycle; or
- a deterministic degree-30 even Chebyshev cosine-like approximation with the same execution shape.
```

For Chebyshev tests, account correctly for the polynomial interval/change-of-basis contract. Using interval `[-1,1]` is acceptable when the purpose is to test the polynomial execution engine itself.

Compare:

```text
Fast decoded values
vs
bignum.Polynomial clear evaluation
```

within a documented tolerance.

Also verify the output Level/Scale still matches the planner oracle.
